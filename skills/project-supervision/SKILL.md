# Project Supervision

実装を指揮するのではなく、プロジェクトが合意したゴールへ進んでいるかを一次資料から評価する。監督レポートは派生情報であり、要件、Issue、PR、CIの正本を置き換えない。

## 権限境界

- 既定では読み取り専用で調査し、状態変更や実装を行わない。
- Issue、Project、Pull Request、branch、commit、merge、通知の変更は、それぞれユーザーとリポジトリ規則が許可した場合だけ行う。
- 監督役は、実装役やレビュー役の自己申告だけでDoneを判定しない。
- 不明な情報を推測で補完せず、証拠不足または判断待ちとして報告する。

## 監督ワークフロー

1. Projectの目標、対象Milestone、正本、承認境界を確認する。
2. 要件、設計、ADR、Issue、Sub-issue、Pull Request、対象commitのCIを収集する。
3. 目的から実装までの対応、依存関係、状態遷移、レビュー状況を照合する。
4. Pull Requestの大きさと関心事の凝集度を確認し、分割またはStacked PRが必要か評価する。
5. Stacked PRがある場合は、Stack全体と各レイヤーを別々に評価する。
6. 現在地、ゴールとの差、最大リスク、判断待ち、次の優先事項を報告する。
7. 状態更新を依頼されている場合だけ、報告根拠と対象を示してから反映する。

## 監督観点

- ゴール整合: 完了したIssueがMilestoneの成功条件へ寄与しているか。
- トレーサビリティ: 要件、設計、Issue、PR、テストに欠落や矛盾がないか。
- 依存関係: Readyの前提が満たされ、Blockedの原因と解除条件が明確か。
- 変更境界: 一つのIssueやPRが複数の設計判断を抱えていないか。
- レビュー可能性: 差分、説明、テストがレビュー可能な単位か。
- 検証: 正常系、異常系、統合経路が対象commitに対して確認されているか。
- 判断記録: 要件や設計の変更が正本とADRへ反映されているか。
- 再開可能性: 別セッションが次の作業と未解決事項を再構成できるか。

## Stacked PRの監督

公式`gh stack`が導入され、Stackをローカルに取得できる場合は、読み取り用途に`gh stack view --json`を使う。裸の`gh stack view`はTTYでUIを開く可能性があるため使わない。

公式`gh-stack` Skillも利用可能なら併用し、状態スキーマと障害時の解釈はその現行版を優先する。

次を確認する。

- Stackが一つの変更ストーリーである。
- 基盤レイヤーが下、依存するレイヤーが上に並ぶ。
- 各PRが一文で説明でき、単独レビューと単独検証が可能である。
- 各PRのbaseが直下のbranchで、最下位だけがtrunkを向く。
- 下位レイヤー変更後に上位レイヤーが追従し、`needsRebase`が放置されていない。
- 各レイヤーのCIに加え、Stack最上位または統合用レイヤーで全体経路を検証する。
- 下位PRの公開契約に未解決指摘がある場合、影響する上位PRの完了判定を保留する。
- Stackへ無関係な修正が混入していない。

`gh stack`が利用できない場合は、PRのbase branch、依存記述、commit ancestryから同等の連鎖を確認し、取得できなかった情報を明記する。

`gh stack sync`はfetch、rebase、push、PR状態同期を行い、`gh stack merge`は複数PRをマージするため、読み取り専用監督では実行しない。非対話実行では、Stackの分岐により`sync`が変更せず終了コード0を返す場合があるため、許可された実行後も出力と`view --json`を再確認する。

## 巨大PRの判定

行数やファイル数だけで機械的に判断しない。次のいずれかがあれば分割候補とする。

- 独立した複数の設計判断が含まれる。
- 公開契約、計算コア、通信境界、統合検証など異なるレビュー観点が混在する。
- レビュワーが差分の一部を承認しても残りを保留できない。
- 要件とテストの対応を一つのPR内で説明できない。
- 基盤変更とその利用側が分離可能で、明確な依存順序を持つ。

順序依存する一つのストーリーならStacked PR、独立しているなら別Issue・別PR・別Stackを提案する。

## 重要度と状態提案

- Critical: データ損失、セキュリティ、主要要件違反、誤ったmerge、または最新commitの必須検証欠落により、作業を進めてはいけない。
- High: 設計・公開契約・受け入れ条件の不整合など、完了判定前に解消が必要である。
- Medium: レビュー可能性、保守性、診断性を大きく損なうが、直ちに作業停止までは不要である。
- Low: 明確さや運用効率の改善であり、別途追跡してもよい。

Criticalまたは作業継続不能な外部依存には`Blocked`を提案する。修正が必要なレビュー指摘には`In Progress`、根拠が揃ったレビュー待ちには`Review`を提案する。必須CI、最新commitへのレビュー、受け入れ条件、依存PRが揃うまで`Done`を提案しない。正式な状態変更権限と既存Projectの遷移規則を優先する。

## 出力

`assets/supervision-report.md`を必要な範囲だけ使い、重要度順に次を報告する。

- 現在地とゴールとの差
- 重大な逸脱またはリスクと根拠
- Blocked、判断待ち、証拠不足
- PRまたはStackのレビュー状態
- 次に優先すべきIssueまたは人間の判断
- 完了判定と残存不確実性

問題が見つからない場合も、確認した範囲と未確認の外部条件を区別する。
