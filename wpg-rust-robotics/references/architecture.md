# アーキテクチャ

## Functional core / imperative shell

処理を次の順で読める形にする。

```text
入力値 → 検証 → 正規化・制御・軌道計算 → 出力値 → 通信／シミュレーション／保存／描画
```

- 公開APIは名前付きの値型で表し、ライブラリ固有型を境界外へ漏らさない。
- 外部状態を読まない計算を純粋関数へ切り出す。
- 時間発展の状態は小さな値型にまとめ、状態遷移の物理的意味を明確にする。
- 可変状態や`map`、`scan`を目的化せず、数式との対応を優先する。
- 失敗は`Result`と判断可能なエラー型で表す。
- 入力境界で非有限値、欠落、重複、周期比、単位の不整合を検証する。
- 浮動小数点時刻の累積誤差を避けられる場合は、サンプル番号から時刻を算出する。

## Rustとworkspace

- Rust初学者にも分かるよう、単位、座標系、配列要素、式の目的をdoc commentへ書く。
- `main.rs`は入力準備、ライブラリ呼び出し、副作用実行だけの薄い層にする。
- 計算、シミュレーション、ロギングを必要に応じて別クレートへ分ける。
- 複数クレートはCargo workspaceで管理し、ルートの`Cargo.lock`を使用する。
- `lib.rs`を読みやすく保つため、単体テストは`src/test.rs`または`src/tests.rs`へ分離する。

## 移植とDora

- 移植元との数値互換性が必要なら、代表入力の固定値回帰テストを保持する。
- 移植元の欠陥を再現しない場合は、安全な終了条件と差異をdoc commentへ記録する。
- ROS 2やDoraのメッセージ型を計算コアへ持ち込まず、境界で値型へ変換する。
- Doraのポート名やスキーマが未確定なら、仮の型をコアへ追加せず境界案として扱う。
- 制御、シミュレーション、ロギングの周期とプロセス責務を明示する。
